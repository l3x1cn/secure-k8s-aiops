## Context

## Approach

Wszystkie taski należą do stosu „pozostałe”: bash, Makefile, Dockerfile, YAML. Taski 1 i 2 są od siebie niezależne. Task 3 wymaga obu: CI woła skrypt z Task 1, a obrazy muszą już przechodzić bramkę z Task 2. Kolejność: 1 → 2 → 3. Każdy task zostawia działające drzewo, a `make lint unit manifests` przechodzi po każdym z nich.

Decyzje wspólne:
- **Jeden skan na cel.** Skan zapisuje JSON ze wszystkimi poziomami; obraz skanuje się z `--ignore-unfixed`.
  - SARIF powstaje z JSON przez `trivy convert`.
  - Bramka to `trivy convert --severity HIGH,CRITICAL --exit-code 1` na tym samym JSON. Daje ten sam wynik co polecenia z issue, a JSON i SARIF opisują dokładnie to, co ocenia bramka (decyzja 2).
  - Kod różny od 0 z samego skanu to błąd Trivy, więc bramka zamyka się bezpiecznie.
- **Bez `aquasecurity/trivy-action`, bez cache bazy Trivy w CI** (każdy job pobiera DB z `mirror.gcr.io`) i bez zmian rulesetu.
- **Bez osobnego celu make dla obrazów.** Lokalnie obraz skanuje `bash scripts/trivy.sh image <nazwa> <obraz>` (opis w nagłówku skryptu). `make trivy-config` istnieje, bo job `manifests` uruchamia cel make (konwencja `ci.yml`).
- **`jdx/mise-action` w `images.yml` ma `cache: false`.** Workflow publikuje obrazy, więc binarka Trivy nie może pochodzić z cache zapisanego przez inny przebieg. `ci.yml` zostaje z domyślnym cache.
- **Kolejność w `push`:** build z `load` → bramka → artefakt → `docker/login-action` → build z `push`. Gdy działa Trivy, dane logowania do GHCR nie istnieją jeszcze w `~/.docker/config.json`.
- **SARIF wysyłamy w PR i na `main`.** Kategorie: `trivy-config` oraz `trivy-image-<nazwa>`. Job `sarif` startuje z `!cancelled()`, pobiera artefakt przez `pattern` i pomija upload, gdy SARIF nie istnieje (obraz się nie zbudował). Dzięki temu nie dokłada czerwonego joba do błędu budowy.
- **Bez obsługi PR z forków.** Token takiego PR jest tylko do odczytu, więc upload może się nie udać. Job `sarif` nie jest wymagany, więc nie blokuje scalenia.

### Task 1: Bramka Trivy: scripts/trivy.sh, .trivyignore i make trivy-config
**Commit:** feat(security): bramka Trivy dla obrazów i deploy/ (scripts/trivy.sh, .trivyignore) (T15)

**Files:**
- Create: `scripts/trivy.sh`
- Create: `.trivyignore`
- Modify: `Makefile`

1. Utwórz `scripts/trivy.sh` z treścią poniżej i nadaj mu tryb wykonywalny (`chmod +x scripts/trivy.sh`; w git `100755`, jak `scripts/manifests.sh`, `doctor.sh` i `secrets.sh`). Makefile i CI wołają go przez `bash`.

```bash
#!/usr/bin/env bash
# Bramka Trivy (T15): jeden skan obrazu albo katalogu deploy/ Trivy z mise.toml. Wyniki ze wszystkimi poziomami
# trafiają do reports/trivy/: <cel>.json (raport testów, T31) i <cel>.sarif (GitHub code scanning, job sarif w CI).
# Bramka to `--severity HIGH,CRITICAL --exit-code 1` na wyniku skanu (`trivy convert`), a obraz skanuje się
# z `--ignore-unfixed`, więc blokują tylko podatności z dostępną poprawką. Log pokazuje tabelę tego, co blokuje.
# Kod 1: znalezisko HIGH albo CRITICAL, błąd skanu albo .trivyignore niezgodny z regułą poniżej; kod 2: złe argumenty.
# Użycie:
#   make trivy-config                             # = scripts/trivy.sh config; job manifests w ci.yml
#   bash scripts/trivy.sh image <nazwa> <obraz>   # obraz z lokalnego Dockera (--image-src docker); joby build
#                                                 # i push w images.yml, lokalnie np. po make images:
#                                                 # bash scripts/trivy.sh image orders ghcr.io/l3x1cn/secure-k8s-aiops/orders:dev
# .trivyignore (korzeń repozytorium; Trivy czyta go z bieżącego katalogu): każdy wpis stoi w grupie pod komentarzem
# z uzasadnieniem (bez pustej linii między komentarzem a wpisami) i kończy się datą przeglądu exp:RRRR-MM-DD.
# Po tej dacie Trivy przestaje stosować wpis, więc bramka znów zgłasza znalezisko.
# Zgodny z bash 3.2 (macOS).
set -euo pipefail

cd "$(dirname "$0")/.."

# Trivy i yq w wersjach z mise.toml mają pierwszeństwo przed systemowymi, także bez make i bez aktywacji mise
# w powłoce (jak PATH w Makefile).
PATH="$(mise bin-paths 2>/dev/null | tr '\n' ':')$PATH"

out=reports/trivy

usage() {
  echo "Użycie: $0 config | image <nazwa> <obraz>" >&2
  exit 2
}

# Reguła .trivyignore (T15): linia wpisu musi należeć do grupy otwartej komentarzem (pusta linia zamyka grupę)
# i kończyć się exp:RRRR-MM-DD. Wypisuje każde naruszenie z numerem linii; kod 1, gdy jest choć jedno.
check_ignorefile() {
  [ -f .trivyignore ] || return 0
  awk '
    /^[ \t]*$/ { group = 0; next }
    /^[ \t]*#/ { group = 1; next }
    {
      if (!group || $0 !~ /[ \t]exp:[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][ \t]*$/) {
        printf ".trivyignore:%d: wpis bez komentarza z uzasadnieniem nad grupą albo bez exp:RRRR-MM-DD: %s\n", NR, $0 > "/dev/stderr"
        bad = 1
      }
    }
    END { exit bad }
  ' .trivyignore
}

[ $# -ge 1 ] || usage
case $1 in
  config)
    [ $# -eq 1 ] || usage
    name=config
    target=deploy/
    scanners=misconfig
    ;;
  image)
    [ $# -eq 3 ] || usage
    name=image-$2
    target=$3
    scanners=vuln,secret
    ;;
  *)
    usage
    ;;
esac

if ! check_ignorefile; then
  echo "Popraw .trivyignore według reguły z jego nagłówka." >&2
  exit 1
fi

mkdir -p "$out"
json=$out/$name.json
sarif=$out/$name.sarif
# Stary wynik z poprzedniego uruchomienia nie może udawać nowego.
rm -f "$json" "$sarif"

# Skan bez filtra poziomów i bez --exit-code: każdy kod różny od 0 to błąd Trivy (set -e kończy skrypt).
# --skip-version-check: bez zapytania o nowszą wersję (wersję wyznacza mise.toml).
if [ "$1" = config ]; then
  trivy config --skip-version-check --format json --output "$json" "$target"
else
  trivy image --skip-version-check --image-src docker --no-progress --ignore-unfixed --format json --output "$json" "$target"
fi

trivy convert --quiet --format sarif --output "$sarif" "$json"
if [ "$1" = config ]; then
  # Trivy podaje ścieżki względem deploy/ z uriBaseId, a code scanning czyta uri względem korzenia repozytorium
  # i pomija uriBaseId (github/codeql-action#2215): bez prefiksu alert wskazuje nieistniejący plik.
```

```bash

RUN_IMG=$(gh run list --repo "$R" --workflow images.yml --event push --commit "$MAIN_SHA" --limit 1 --json databaseId --jq '.[0].databaseId')

  for run in "$RUN_CI" "$RUN_IMG"; do

    echo "artefakty $run: $(gh api "repos/$R/actions/runs/$run/artifacts" --jq '[.artifacts[].name | select(startswith("trivy-"))] | sort | join(" ")')"
```

```bash
  for n in frontend orders fault-runner; do
    joblog "$RUN_IMG" "push ($n)"

  done
  echo "code scanning, main, commit $MAIN_SHA:"
  gh api "repos/$R/code-scanning/analyses?ref=refs/heads/main&tool_name=Trivy&per_page=50" --jq ".[] | select(.commit_sha == \"$MAIN_SHA\") | \"\(.category) wyniki=\(.results_count)\"" | sort -u
  echo "otwarte alerty Trivy na main: $(gh api "repos/$R/code-scanning/alerts?ref=refs/heads/main&tool_name=Trivy&state=open&per_page=100" --jq 'group_by(.rule.security_severity_level) | map("\(.[0].rule.security_severity_level)=\(length)") | join(" ")')"
  echo "zakładka Security: https://github.com/$R/security/code-scanning?query=is%3Aopen+branch%3Amain+tool%3ATrivy"
  for n in frontend orders fault-runner; do
    tok=$(curl -fsS "https://ghcr.io/token?scope=repository:$IMG/$n:pull" | jq -r .token)
    echo "GHCR $n:$TAG → HTTP $(curl -s -o /dev/null -w '%{http_code}' -H "Authorization: Bearer $tok" -H 'Accept: application/vnd.oci.image.index.v1+json,application/vnd.oci.image.manifest.v1+json' "https://ghcr.io/v2/$IMG/$n/manifests/$TAG")"
  done
} | tee reports/t15-main.txt
```

## Assumptions & contingencies

Założenia (właściciel może je zmienić):
- Cztery decyzje właściciela z Context: Dockerfile'e z `apt-get upgrade` i bez pip, SARIF/JSON ze wszystkimi poziomami, osobne joby `sarif`, reguła `.trivyignore` w skrypcie.
- SARIF trafia do code scanning także z PR, więc PR dostaje adnotacje i kontrolę code scanning. Ta kontrola nie jest wymagana.
- Alertów MEDIUM/LOW z `deploy/` nikt nie odrzuca w T15. Część z nich to fałszywe alarmy: tag i namespace ustawia kustomize (KSV-0013, KSV-0110).
- Trivy zostaje w wersji 0.76.0, choć wyszła 0.76.2; issue wymaga 0.76.0.
- Bez cache bazy Trivy w CI: każdy job pobiera ją z `mirror.gcr.io`.
- `.trivyignore` nie ma wpisów w chwili dostarczenia.

Plan awaryjny:
- **Pin codeql-action.** Jeśli Task 3 powstaje przed 2026-11-11T16:49Z (`date -u`), pinem jest v4.39.2: `github/codeql-action/upload-sarif@1fc58d04a4d4374f921bdac573c3811c240f9c26 # v4.39.2`. W obu plikach i w opisie PR zmień tylko tę linię i numer wersji.
- **Krok 4 Verification albo bramka w PR T15 albo na `main` zgłasza HIGH/CRITICAL w obrazie**, bo między sprawdzeniem a dostarczeniem doszła nowa podatność:
  - Pakiet Debiana, którego `apt-get upgrade` nie instaluje (poprawka tylko w point release albo `proposed-updates`): wpis w `.trivyignore`:
    - komentarz: `# <pakiet> <zainstalowana wersja>: poprawka <wersja> jeszcze poza trixie-security; apt-get upgrade w Dockerfile'ach zainstaluje ją po wydaniu`;
    - wpis: `<ID> exp:<dziś + 30 dni>`;
    - osobny commit `fix(images): wyjątek Trivy <ID> do <data> (T15)`.
  - Pakiet z venv (`app/.venv/…`, zależność z `uv.lock`):
    - `uv lock --upgrade-package <pakiet>`. Gdy rozwiązana wersja ≥ `FixedVersion`: `make unit`, commit `fix(deps): <pakiet> <wersja> (bramka Trivy, T15)`;
    - gdy ograniczenia w `pyproject.toml` na to nie pozwalają: wpis w `.trivyignore` z uzasadnieniem i `exp:<dziś + 30 dni>`.
  - Interpreter CPython, binarki obrazu bazowego albo cokolwiek innego: zatrzymaj się i zgłoś właścicielowi znalezisko z JSON. Podbicie Pythona (obraz bazowy i `mise.toml`) to decyzja poza T15.
  - Na `main` (publikacja wstrzymana): poprawkę dostarcz osobnym PR z gałęzi `t15-fix-<pakiet>`. Kryterium 2 dowodzi wtedy przebieg na commicie tego PR, a w dowodzie podaj oba PR.
- **Błąd pobierania bazy Trivy albo checks bundle** (`TOOMANYREQUESTS`, timeout), obrazu z Docker Hub albo pakietów z PyPI lub Debiana: jeden raz `gh run rerun <run> --repo "$R" --failed`. Ponowny błąd: zatrzymaj się i zgłoś log kroku.
- **`upload-sarif` kończy się 403 albo 404** z komunikatem o wyłączonym code scanning albo Advanced Security:
  - narzędziem `ask` poproś właściciela, żeby włączył code scanning dla repozytorium (Settings → Advanced Security → Code scanning);
  - potem `gh run rerun <run> --repo "$R" --failed`;
  - inny błąd przetwarzania SARIF: zatrzymaj się i zgłoś log joba `sarif`. Bramki nie zmieniaj.
- **zizmor zgłasza uwagi w domyślnej personie:**
