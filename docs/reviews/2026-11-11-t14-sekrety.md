### [LOW] MAINT-001: detektor Secretów pomija `kind: SecretList`, który kubectl stosuje jako Secrety

**ID:** MAINT-001
**Location:** `tests/security/test_secrets.py:24-36`
**Category:** Maintainability
**Effort:** trivial

**Problem:**
`secrets_with_values` otwiera tylko `kind == "List"` (linie 28-30), a każdy inny rodzaj bez `Secret` zwraca `[]` (linie 31-32). kubectl rozwija każdy dokument z `items` jako listę i uzupełnia brakujący `kind` elementu rodzajem listy bez przyrostka `List`. `SecretList` z elementami bez `kind` jest więc dla kubectl listą Secretów, a `test_deploy_files_have_no_secret_values` go przepuszcza. gitleaks też go nie zgłasza dla składni w linii (`no leaks found`). Test overlayów łapie ten przypadek tylko wtedy, gdy plik dołącza kustomization. Nagłówek testu (linie 4-5) obiecuje pokrycie plików, „których nie dołącza żaden kustomization”.

**Impact:**
Ręcznie napisany albo przekonwertowany `SecretList` wrzucony do `deploy/` poza kustomization przechodzi test. Wiersz Z4 w `docs/bezpieczenstwo.md` ma stan „działa”, a opis w `docs/architektura.md:219` mówi o braku Secretu z `data` w plikach `deploy/`. Waga LOW: `kubectl get … -o yaml` daje `kind: List`, który jest pokryty.

**Remediation:**
Obsłuż każdy rodzaj `*List` z `items` i przekazuj rodzaj elementu w dół, jak apimachinery: tylko gdy element nie ma ani `kind`, ani `apiVersion`. Dodaj mutację z `SecretList` do kroku 2a Verification.

```python
# Before
def secrets_with_values(document: object) -> list[str]:
    if not isinstance(document, dict):
        return []
    if document.get("kind") == "List":
        items = document.get("items") or []
        return [found for item in items for found in secrets_with_values(item)]
    if document.get("kind") != "Secret":
        return []

# After
def secrets_with_values(document: object, item_kind: str | None = None) -> list[str]:
    if not isinstance(document, dict):
        return []
    kind = document.get("kind", item_kind)
    if isinstance(kind, str) and kind.endswith("List") and "items" in document:
        inherited = kind.removesuffix("List") or None
        items = document.get("items") or []
        return [
            found for item in items for found in secrets_with_values(item, inherited)
        ]
    if kind != "Secret":
        return []
```

### [LOW] MAINT-002: komentarz `grafana-password` obiecuje bezpieczne podstawienie w powłoce, ale `make -C` i sub-make dopisują linie katalogu na stdout

**ID:** MAINT-002
**Location:** `Makefile:137-140`
**Category:** Maintainability
**Effort:** trivial

**Problem:**
Komentarz w linii 138 mówi: „Wypisuje tylko hasło i znak nowego wiersza, więc nadaje się do podstawienia w powłoce.” GNU make włącza `-w` automatycznie przy `-C` i w sub-make, a Makefile nie ustawia `--no-print-directory` w `MAKEFLAGS`. `make -C <katalog> grafana-password` wypisuje „Entering directory” i „Leaving directory” na stdout, więc `pw=$(make -C <repo> grafana-password)` przechwytuje trzy linie. Wywołanie z README (`make grafana-password` w korzeniu repozytorium) wypisuje tylko hasło i nowy wiersz. To samo dotyczy `make gitleaks` wywoływanego z `test_history_has_no_leaks` pod nadrzędnym make (T26): test sprawdza tylko kod wyjścia, więc zmienia się tylko komunikat błędu.

**Impact:**
Skrypty wywołujące cel spoza repozytorium albo z innego celu dostają błędny ciąg hasła, mimo że komentarz mówi, że tak nie będzie.

**Remediation:**
Wariant A sprawia, że komentarz jest prawdziwy w obu ścieżkach (po nim jawne `--no-print-directory` w `up` jest zbędne, ale niegroźne). Wariant B zawęża tylko komentarz.

```make
# Before (początek Makefile): brak

# After, wariant A
# Bez „Entering directory” także przy make -C i w sub-make: make grafana-password wypisuje samo hasło.
MAKEFLAGS += --no-print-directory

# After, wariant B (linia 138)
# Z katalogu repozytorium (bez -C) wypisuje tylko hasło i znak nowego wiersza, więc nadaje się do podstawienia w powłoce. …
```
