### [LOW] SEC-001: CI pins mise 2026.10.13, affected by GHSA-43hx-4j66-v486 (trust bypass via a `path:` tool version) [verified]

**ID:** SEC-001
**Location:** `.github/workflows/ci.yml:26`
**Category:** Security
**OWASP:** A03:2025
**CWE:** CWE-1395
**Effort:** trivial

**Problem:**
All four `jdx/mise-action` steps (`ci.yml:26,41,55,67`) pin `version: "2026.10.13"`. The advisory (rated high, published 2026-10-29) covers mise < 2026.10.14: a `path:` tool version in an untrusted `mise.toml` skips the trust check and goes first on PATH. `mise.toml:5-6` ties the CI version to `min_version = "2026.10.13"` and `README.md:22` repeats it, so the developer floor stays at a vulnerable release. The locally installed mise is 2026.10.25 (patched). The challenger lowered the severity from MEDIUM: in CI the pull request already controls the Makefile and the workflow, and the token is read-only, so the gain there is negligible. This diff adds no new exposure; it adds a pin of a release with a known advisory.

**Impact:**
A reviewer with mise 2026.10.13 who checks out a fork PR whose `mise.toml` declares `git = "path:./.x"` would run attacker code first on PATH without a trust prompt [INFERENCE: not demonstrated].

**Remediation:**
Raise the CI version, `min_version` and `README.md:22` together to a patched release (at least 2026.10.14; 2026.10.25 was tested locally). `mise.toml:5` already requires changing them together. Combine this with MAINT-003 so the version is written once.

```yaml
version: "2026.10.25"   # ci.yml, all four steps
```

### [LOW] SEC-002: The `secrets` job never scans content added in merge commits [verified]

**ID:** SEC-002
**Location:** `Makefile:36`
**Category:** Security
**OWASP:** A06:2025
**CWE:** CWE-693
**Effort:** easy

**Problem:**
gitleaks 8.30.1 runs `git log -p -U0 <log-opts>`, which prints no patch for merge commits. On the repo's own merge commit `be50c49`, `gitleaks git --log-opts="-1 be50c49"` scans 0 commits; with `--diff-merges=first-parent` it scans 1 commit (about 281 KB). The project merges `main` into feature branches. Commits brought in by the merge are scanned on their own, so only content added while resolving a conflict is missed. The comments in `Makefile:33` ("Sekrety w całej historii HEAD") and `ci.yml:50` promise the whole history.

**Impact:**
A credential placed in a merge-conflict resolution passes `secrets`. GitHub push protection (enabled) remains as a second layer for provider-known patterns.

**Remediation:**
Scan merge diffs against the first parent and keep the comments accurate. The auditor checked that this exits 0 on HEAD.

```make
gitleaks:
	gitleaks git --no-banner --redact --verbose --log-opts="--diff-merges=first-parent HEAD" .
```

**ID:** SEC-003

**Category:** Security
**OWASP:** A08:2025
**CWE:** CWE-345
**Effort:** easy

### [LOW] SEC-004: The gate binaries (gitleaks, kustomize, kubeconform) are installed by version only: no `mise.lock`, no attestation [verified]

**ID:** SEC-004
**Location:** `.github/workflows/ci.yml:56`
**Category:** Security
**OWASP:** A03:2025
**CWE:** CWE-494
**Effort:** medium

**Problem:**
mise reports a sha256 checksum for these three tools, taken from the same GitHub release as the binary; ruff, uv and python also have attestations. The repo has no `mise.lock`; `mise-action` v5.2.6 adds `--locked` only when a lock file exists.

**Impact:**
Whoever controls an upstream release can replace the asset and its checksum for the pinned version, and then `secrets` and `manifests` can always pass (the model incident in `ci.yml:5` is trivy-action, CVE-2026-33634).

**Remediation:**
Commit a `mise.lock` with per-platform checksums; `mise-action` then runs `mise install --locked`. A change to the toolchain gets a larger PR (the lock must be regenerated on every version bump), so the owner should decide.

```bash
mise lock --platform linux-x64,linux-arm64,macos-x64,macos-arm64
git add mise.lock
```

### [LOW] MAINT-003: The mise version is written four times in `ci.yml` [verified]

**ID:** MAINT-003
**Location:** `.github/workflows/ci.yml:26`
**Category:** Maintainability
**Effort:** trivial

**Problem:**
The same value is at `ci.yml:26,41,55,67`, in `mise.toml:6` and in `README.md:22`. Only two comments tie them together (`mise.toml:5`, `ci.yml:4`), and Dependabot does not update `with:` inputs.

**Impact:**
A partial bump (see SEC-001) fails nothing: each job installs whatever its own `version:` says.

**Remediation:**
Define the version once at workflow level. The name avoids the `MISE_` prefix, which mise reads for its own settings.

```yaml

      - uses: jdx/mise-action@f5be966e4a917d54244728e6a5fdcd1d93a35e6c # v5.2.6
        with:
          version: ${{ env.CI_MISE_VERSION }}
```
