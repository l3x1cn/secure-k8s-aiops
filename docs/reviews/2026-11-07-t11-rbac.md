### [MEDIUM] DOC-001: RBAC contract opens with an untrue "no pod talks to the cluster API" claim

**ID:** DOC-001
**Location:** `docs/architektura.md:64`
**Category:** Documentation
**Drift-class:** decision
**Fix-policy:** needs-decision
**Effort:** trivial

**Problem:**
The new section starts with "Żaden pod nie rozmawia z API klastra". That is not true of the platform, and this document is the shared contract for T01–T36. Cilium and Hubble in kube-system run now and use the API; kube-prometheus-stack (T16) and Grafana Alloy (T17, events via `loki.source.kubernetes_events`) are planned and need it too. What T11 delivers and tests is narrower: the `app.kubernetes.io/part-of=secure-k8s-aiops` Deployments (`tests/security/test_rbac.py`, `test_own_pods_have_no_service_account_token`). The next paragraph (`docs/architektura.md:66`) and the issue's acceptance criterion ("w żadnym własnym podzie") use that scope; the opening sentence drops the qualifier. The `default` ServiceAccounts are unchanged and there is no admission control, so only the test catches drift.

**Impact:**
Someone implementing T16 or T17 could read the contract literally and think chart-provided ServiceAccounts and RBAC break it. A reader could also assume the cluster enforces the rule for every pod.

**Remediation:**

```markdown
<!-- Before -->
Żaden pod nie rozmawia z API klastra, a członkowie zespołu dostają tylko odczyt (T11).

<!-- After -->
Żaden własny pod (workloady z tabeli poniżej) nie rozmawia z API klastra, a członkowie zespołu dostają tylko odczyt (T11). Komponenty platformy (Cilium, później charty z T16 i T17) mają konta i RBAC z własnych chartów, poza tym kontraktem; regułę dla własnych podów egzekwuje tylko test.
```

### [LOW] SEC-001: Test matrix does not guard the documented attach, port-forward, proxy and token exclusions

**ID:** SEC-001
**Part-of:** COMP-001
**Location:** `tests/security/test_rbac.py:84`
**Category:** Security
**OWASP:** A01:2025
**CWE:** CWE-693
**Effort:** easy

**Problem:**
`docs/architektura.md:84` and `deploy/base/rbac/sre-readonly.yaml:7-8` promise that `sre-readonly` has "z podzasobów tylko pods/log, bez exec, attach, port-forward i proxy". `MATRIX` tests only `create pods/exec` (lines 54, 89) and `get nodes/proxy` (line 90); `DEVELOPER_DENIED` (lines 51-58) has the same gap. ### [LOW] SEC-002: `test_service_accounts_have_no_rbac_bindings` misses `User` subjects and the all-account groups

**ID:** SEC-002
**Location:** `tests/security/test_rbac.py:184`
**Category:** Security
**OWASP:** A01:2025
**CWE:** CWE-693
**Effort:** easy

**Problem:**
The contract says "bez Role ani bindingów" (`deploy/base/rbac/serviceaccounts.yaml:1-2`). Lines 184-185 match only `kind: ServiceAccount` subjects and the `system:serviceaccounts:<ns>` groups. RBAC also applies a `kind: User` subject named `system:serviceaccount:<ns>:<name>` to that account. [INFERENCE: from how the RBAC authorizer matches subjects; such a binding was not created on the cluster.] The matrix rows (lines 92-96) probe only `list secrets` and `get pods`, so any other permission granted this way goes unnoticed. Plan Verification step 7 mutates only the `--serviceaccount` form.

**Impact:**
`kubectl -n shop create rolebinding x --role=deployer --user=system:serviceaccount:shop:frontend` gives the account, say, create on deployments, and every test stays green. Exploiting it also needs a token, which the Deployments do not mount, so a second change is required first.

**Remediation:**

```python
# Before
if (subject["kind"] == "ServiceAccount" and account in accounts) or (
    subject["kind"] == "Group" and subject["name"] in namespace_groups
):

# After
sa_users = {f"system:serviceaccount:{ns}:{name}" for ns, name in SERVICE_ACCOUNTS}
...
if (
    (subject["kind"] == "ServiceAccount" and account in accounts)
    or (subject["kind"] == "User" and subject["name"] in sa_users)
    or (subject["kind"] == "Group" and subject["name"] in namespace_groups)
):
```

Do not add `system:serviceaccounts` or `system:authenticated` to the groups without an allow-list keyed on the four built-in ClusterRoleBindings (`system:service-account-issuer-discovery`, `system:basic-user`, `system:discovery`, `system:public-info-viewer`) and applied only to the Group match, or the test always fails (and a name-only skip would hide a namespaced binding with a built-in name).

### [LOW] MAINT-001: A "deny" row passes when the resource name does not exist

**ID:** MAINT-001
**Location:** `tests/security/test_rbac.py:127`
**Category:** Maintainability
**Effort:** trivial

**Problem:**
`kubectl auth can-i` answers `no` on stdout for an unknown resource and prints `Warning: the server doesn't have a resource type 'deploymnets' in group 'apps'` only on stderr (checked on the cluster); `can_i` reads only stdout. Any `(…, False)` row with a typo passes without testing anything. A positive row with a typo fails as `assert False is True` without the warning, so the plan's contingency message never appears. An unknown subresource (`--subresource=exce`) gets `no` with no warning at all. (Severity lowered from MEDIUM by the challenger: all 11 resource names in `MATRIX` resolve today, so there is no current impact.)

**Impact:**
A future deny row can be vacuous while the suite looks green, against the test's own rule that a security test must not look green when it did not run.

**Remediation:**

```python
# Before
result = kubectl(*args, *identity(who), check=False)
answer = result.stdout.strip()

# After
result = kubectl(*args, *identity(who), check=False)
if "doesn't have a resource type" in result.stderr:
    pytest.fail(f"kubectl {' '.join(args)}: {result.stderr.strip()}")
answer = result.stdout.strip()
```

Keep subresource rows to the known `log`, `exec` and `proxy`; COMP-001 covers subresources from the rules.

### [LOW] MAINT-002: The "reads every resource" test checks only `list`

**ID:** MAINT-002
**Part-of:** COMP-001
**Location:** `tests/security/test_rbac.py:161`
**Category:** Maintainability
**Effort:** trivial

**Problem:**
`docs/architektura.md:84` and `deploy/base/rbac/sre-readonly.yaml:1` promise get, list and watch on every resource. `test_sre_reads_every_listable_resource_except_secrets` calls only `can_i("sre", "list", r, None)`, and `MATRIX` has `get` or `watch` rows for 3 resources. A future rule with `verbs: [list]` passes.

**Impact:**
A rule cut down to `[list]` goes unnoticed. Today every rule is `[get, list, watch]`.

**Remediation:**

```python
# After

    f"{verb} {r}"
    for r in resources
    if r != "secrets"

    if not can_i("sre", verb, r, None)
]
```

About 55 ms per call, so the test goes from about 4 s to about 13 s. COMP-001 covers the same invariant without the probes.

### [LOW] COMP-001: The read-only contract of the team roles is checked only by sampled `can-i` probes

**ID:** COMP-001
**Location:** `tests/security/test_rbac.py:161`
**Category:** Composite
**Effort:** easy
**Composed-of:** SEC-001, MAINT-002
**Origin:** review

**Problem:**
`docs/architektura.md:84` and the role headers (`sre-readonly.yaml:1,7-8`, `developer.yaml:1-3`) promise three things: get, list and watch only; no secrets; no subresource except `pods/log`. RBAC has no deny rules, so "nothing else" can only be proven from the rule set itself, but the tests check samples of answers: six sre and six developer deny rows, and one `can-i list` per resource. A sample cannot show absence (SEC-001) or that all three verbs are granted everywhere (MAINT-002). Checked in the files: all 21 rules in `sre-readonly.yaml` and the 3×3 rules in `developer.yaml` have exactly `verbs: [get, list, watch]` and no subresource other than `pods/log`, so a structural test passes today.

**Impact:**
Trivy misses subresource grants under a named API group, so these tests are the only automated guard on `team:sre`'s cluster-wide read access. A role edit adding attach, port-forward, proxy or token, and a rule cut down to `[list]`, both go unnoticed.

**Remediation:**

```python
# After: new test next to test_sre_reads_every_listable_resource_except_secrets
def test_team_roles_are_read_only():
    roles = [get_json("clusterrole", "sre-readonly")] + [
        get_json("role", "developer", "-n", ns) for ns in DEVELOPER_NAMESPACES
    ]
    for role in roles:
        assert "aggregationRule" not in role
        for rule in role["rules"]:
            resources = rule.get("resources", [])
            assert set(rule["verbs"]) == {"get", "list", "watch"}
            assert "*" not in rule["apiGroups"] + resources
            assert "secrets" not in resources
            assert {r for r in resources if "/" in r} <= {"pods/log"}
            assert not rule.get("nonResourceURLs")
            assert not rule.get("resourceNames")
```

Optionally also assert that the only bindings whose subjects include `team:sre` or `team:developers` are `sre-readonly` and the three `developer` bindings. The test count goes from 73 to 74 (plan and PR text).
